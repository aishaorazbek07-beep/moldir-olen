# Мөлдір өлең — разделение на страницы, приём оплат через ApiPay/Kaspi, админка

Дата: 2026-07-27

## 1. Задача

Сайт «Мөлдір өлең» сейчас — один статический файл `moldir-olen (1).html`: hero, жоба, дауыс,
билет, өтінім, формат, плюс три модалки оплаты. Оплаты имитируются `setTimeout` на 1600 мс,
поэтому голос, билет и заявка выдаются всегда, без денег.

Нужно:

1. Разбить блоки на отдельные страницы.
2. Подключить приём оплат через ApiPay (Kaspi Pay).
3. Голос за 200 ₸ засчитывать **только** при подтверждённой оплате.
4. Поднять админку: статистика оплат и ручная корректировка голосов (±1, ±10, ±100).

### Корень прежней проблемы

Прежняя реализация открывала ссылку на оплату в Kaspi и считала возврат пользователя в браузер
признаком успеха. Возврат в браузер не связан с фактом оплаты: человек мог закрыть Kaspi или
нажать «назад», и голос всё равно засчитывался.

Вывод, определяющий архитектуру: **признаком оплаты может быть только сообщение от платёжной
системы, полученное сервером.** Ни редирект, ни возврат в браузер, ни запрос от клиента таким
признаком быть не могут. Поэтому статический сайт без бэкенда задачу решить не может в принципе.

## 2. Решения, принятые с заказчиком

| Вопрос | Решение |
|---|---|
| Хостинг | Next.js (App Router) на Vercel |
| Что оплачивается | голоса (200 ₸), билеты (5 000 / 7 000 / 10 000 ₸), өтінім (30 000 ₸) |
| Способ оплаты | счёт по номеру телефона (не QR, не редирект) |
| Голоса за раз | любое количество одним счётом: N × 200 ₸ |
| Вход в админку | один общий пароль из переменной окружения |
| Корректировка голосов | ±1, ±10, ±100; журнал правок закрытый, только внутри админки |
| База данных | Supabase Postgres |
| Ключи ApiPay | заказчик передаст позже; до этого — режим песочницы |

Цена голоса меняется с 500 ₸ (как в текущей вёрстке) на 200 ₸.

## 3. Как работает ApiPay

Base URL: `https://api.apipay.kz/api/v1`. Аутентификация: заголовок `X-API-Key`.

Схема «счёт по номеру телефона»:

1. `POST /invoices` с телом `{phone_number, amount, description, external_order_id}`.
   Ответ `201` со `status: "processing"` — обработка асинхронная.
2. Счёт появляется в приложении Kaspi у владельца номера, статус становится `pending`.
3. Человек подтверждает оплату в Kaspi.
4. ApiPay присылает webhook `invoice.status_changed` со `status: "paid"`, полем `amount`,
   `external_order_id`, `kaspi_invoice_id`, `paid_at`.
5. Подпись webhook'а: заголовок `X-Webhook-Signature: sha256=<hex>`, HMAC-SHA256 по сырому телу
   запроса на webhook-секрете.
6. Статус можно и опросить: `GET /invoices/{id}`.

Существенные для нас свойства:

- Статусы: `processing` → `pending` → `paid` | `cancelled` | `expired` | `error`.
- Счёт по телефону истекает через 24 часа.
- Webhook ретраится **до 11 раз** (первая доставка + 10 повторов), таймаут 5 секунд на попытку.
  Значит обработчик обязан быть идемпотентным и отвечать быстро.
- Лимит 200 запросов в минуту на ключ, при превышении — `429`.

## 4. Поток оплаты

```
[Браузер]  телефон + количество голосов + команда
    │ POST /api/vote/start
    ▼
[Сервер]   валидирует вход
           считает amount = qty * 200  ← сумму считает сервер, не клиент
           POST /invoices в ApiPay
           INSERT payments(status=pending, expected_amount, meta={team_id, qty})
           отдаёт браузеру только payment_id
    │
    ▼
[Kaspi]    счёт в приложении → человек платит
    │
    ▼
[ApiPay]   POST /api/webhooks/apipay
[Сервер]   ① сверяет HMAC-подпись по сырому телу (timingSafeEqual)
           ② находит payment по external_order_id
           ③ сверяет amount из webhook'а с expected_amount из базы
           ④ INSERT votes ... ON CONFLICT (payment_id) DO NOTHING
           ⑤ payments.status = paid
           отвечает 200 быстро
    │
    ▼
[Браузер]  опрашивает GET /api/payment/{id}/status раз в 2 сек
           видит "paid" → показывает подтверждение и новый счётчик
```

Единственное место в системе, где создаётся запись `votes`, — обработчик webhook'а. Ни один
запрос от браузера не может привести к появлению голоса.

### Страховка от потери webhook'а

Webhook может не дойти: сеть, деплой, сработавший circuit breaker ApiPay. Поэтому
`GET /api/payment/{id}/status`, увидев у себя в базе `pending`, сам вызывает
`GET /invoices/{id}` у ApiPay и сверяет статус. Если ApiPay говорит `paid`, платёж
подтверждается тем же кодом, что и в обработчике webhook'а — общая функция `confirmPayment`,
идемпотентная по построению.

Отдельный cron не нужен: страховка срабатывает как побочный эффект того опроса, который браузер
и так делает. Плюс в том, что это не зависит от тарифа Vercel, где на Hobby cron доступен раз в
сутки.

## 5. Структура страниц

Общая оболочка живёт в `app/layout.tsx` и не перерисовывается при переходах: фон-градиент,
канвас светящейся пыли, парящие буквы-призраки, шапка, таб-бар, полоса прогресса скролла.

| Путь | Содержимое |
|---|---|
| `/` | hero с побуквенной анимацией, бегущая лента, скролл-стих, тизеры разделов |
| `/joba` | о проекте, цифры-счётчики (20 өңір / 60 ақын / 20 команда), главный приз |
| `/dauys` | три команды с заливкой и процентами, оплата голоса |
| `/bilet` | карусель кешей с фокусом центральной карточки, покупка билета |
| `/otinim` | форма заявки + взнос 30 000 ₸ |
| `/format` | четыре шага доды |
| `/tolem/[id]` | страница статуса платежа: её можно сохранить и вернуться позже |
| `/admin` | админка, вход по паролю |

Шапка и таб-бар становятся настоящими ссылками (`next/link`), активный таб определяется по
`usePathname()` вместо `IntersectionObserver`. Вся существующая анимация сохраняется, включая
ветку `prefers-reduced-motion: reduce`.

## 6. Модель данных

```sql
teams
  id, slug, name, place_label, color_index, admin_adjustment int default 0,
  display_order, is_active

payments
  id uuid pk, external_order_id text unique, apipay_invoice_id text,
  kind text check (kind in ('vote','ticket','application')),
  expected_amount int, phone text, status text,
  meta jsonb, created_at, paid_at

votes
  id, payment_id uuid unique references payments, team_id, quantity, created_at

tickets
  id, payment_id uuid unique references payments, show_slug, qty,
  ticket_number text unique, created_at

applications
  id, payment_id uuid unique references payments,
  name, birth_year, region, resume, created_at

vote_adjustments
  id, team_id, delta int, created_at
```

Отображаемое число голосов команды = `SUM(votes.quantity) + teams.admin_adjustment`.

Оплаченные голоса и ручная корректировка хранятся раздельно намеренно: настоящую цифру всегда
можно узнать, а правку — посчитать или откатить.

`UNIQUE` на `votes.payment_id`, `tickets.payment_id`, `applications.payment_id` — это и есть
защита от повторных webhook'ов, на уровне базы, а не на уровне надежд.

## 7. Видимость данных

Публичная часть отдаёт **только итоговое число** голосов на команду. В ответе публичного API нет
ни `admin_adjustment`, ни суммы оплаченных голосов, ни истории правок — этих полей нет в схеме
ответа, поэтому их не видно ни в исходниках страницы, ни во вкладке Network.

Разбивка «оплачено / корректировка / итого» и журнал правок доступны только после входа в
`/admin`.

## 8. Админка

Вход: один пароль из `ADMIN_PASSWORD`, сессия в подписанной httpOnly cookie.

**Оплаты.** Количество платежей и сумма, с разбивкой по видам (голоса / билеты / заявки), за
сегодня и за всё время. Список последних платежей со статусами — видны и `pending`, и `expired`,
чтобы было понятно, сколько людей начали и не завершили оплату.

**Голоса.** По каждой команде три числа: оплачено, корректировка, итого. Кнопки `+1 +10 +100` и
`−1 −10 −100`, применяются сразу. Каждое нажатие пишет строку в `vote_adjustments` со временем.
Журнал показывается на этой же странице, наружу не отдаётся.

**Заявки.** Список оплаченных өтінім с резюме и контактами.

## 9. Защита

- **Подпись webhook'а.** HMAC-SHA256 по сырому телу запроса (`await req.text()` до разбора JSON),
  сравнение через `timingSafeEqual`. Неверная подпись — `401`, ничего не пишем.
- **Сверка суммы.** Ожидаемая сумма считается и хранится на сервере при создании счёта. Голос
  засчитывается только если сумма в webhook'е совпала. Клиент не может прислать «10 голосов за
  200 ₸».
- **Идемпотентность.** `UNIQUE` по `payment_id` плюс `ON CONFLICT DO NOTHING`. Одиннадцать
  ретраев ApiPay дают один голос.
- **Ключи.** `APIPAY_API_KEY` и `APIPAY_WEBHOOK_SECRET` только на сервере, в клиентский бандл не
  попадают.
- **Частота.** Ограничение на создание счетов по IP и по номеру телефона — чтобы нельзя было
  засыпать чужой номер счетами в Kaspi.
- **Админка.** httpOnly + `secure` + `sameSite=lax` cookie, подпись сессии, все ручки админки
  проверяют её на сервере.

## 10. Тесты

Платёжное ядро пишется тестами вперёд:

- webhook с подделанной подписью не создаёт голос;
- webhook без заголовка подписи не создаёт голос;
- платёж с суммой, не совпавшей с `expected_amount`, не создаёт голос;
- один и тот же webhook, полученный дважды, даёт ровно один голос;
- `confirmPayment`, вызванный и из webhook'а, и из опроса статуса, даёт один голос;
- отображаемое число = оплаченные + корректировка;
- публичный ответ по команде не содержит `admin_adjustment` и разбивки;
- ручки админки без действительной cookie отвечают `401`;
- корректировка голосов пишет строку в `vote_adjustments`.

## 11. Переменные окружения

```
APIPAY_API_KEY           ключ ApiPay
APIPAY_WEBHOOK_SECRET    секрет для проверки подписи webhook'а
APIPAY_BASE_URL          https://api.apipay.kz/api/v1
ADMIN_PASSWORD           пароль админки
ADMIN_SESSION_SECRET     секрет подписи сессионной cookie
DATABASE_URL             Supabase Postgres
PAYMENTS_MODE            sandbox | live
NEXT_PUBLIC_SITE_URL     публичный адрес — нужен для адреса webhook'а
```

Режимов оказалось три, а не два — после чтения документации ApiPay выяснилось, что у них есть
собственная песочница с эндпоинтом `POST /invoices/{id}/simulate-status`:

| Режим | Поведение |
|---|---|
| `offline` | В ApiPay не ходим. Оплата подтверждается локально, но тем же `confirmPayment`. Нужен, пока нет ключей или сети. |
| `sandbox` | Настоящие вызовы ApiPay ключом в ТЕСТ-режиме. Оплата проводится через `simulate-status`, и к нам приходит **настоящий подписанный webhook**. |
| `live` | Боевые счета в Kaspi. `/api/dev/pay` отвечает 404. |

Режим `sandbox` предпочтительнее локальной заглушки: он проверяет боевой путь целиком, включая
сверку подписи, а не отдельную упрощённую ветку.

Отдельно из документации: секрет подписи webhook'а — **не** API-ключ, а самостоятельное значение,
выдаваемое при создании webhook'а в кабинете. Пока оно не задано, обработчик отклоняет все
уведомления. Это осознанный выбор «закрыто по умолчанию»: принимать неподписанные уведомления
означало бы вернуть ровно ту дыру, ради которой всё и переделывалось.

## 12. Вне объёма

- Возвраты платежей (ApiPay умеет, но заказчик не просил).
- Фискальные чеки через Kaspi OFD.
- Редактирование списка кешей и цен билетов через админку — билеты остаются в конфиге кода.
- Лимит голосов на один номер телефона — выбран вариант «любое количество».
- Мультиязычность интерфейса (сайт остаётся на казахском).
