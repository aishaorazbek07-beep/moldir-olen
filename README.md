# Мөлдір өлең

Сайт национального поэтического проекта: отдельные страницы, приём оплат через
ApiPay (Kaspi Pay) и админка.

## Главное про оплату

Раньше сайт открывал ссылку на Kaspi и засчитывал голос, когда человек
возвращался в браузер. Возврат в браузер не связан с фактом оплаты — можно было
закрыть Kaspi, нажать «назад», и голос засчитывался.

Теперь голос, билет и заявка создаются **только** внутри обработчика webhook'а от
ApiPay — `src/app/api/webhooks/apipay/route.ts`. Браузер лишь *спрашивает*
сервер, оплачено ли; засчитать что-либо он не может. Функция выдачи одна на всю
систему — `confirmPayment` в `src/lib/payments-core.ts`.

Доверие к входящему уведомлению строится в два уровня:

1. **Подпись сошлась** — телу можно верить, проводим сразу.
2. **Подписи нет или она не сошлась** — телу не верим. Считаем его лишь
   подсказкой «глянь счёт такой-то» и запрашиваем статус у ApiPay сами, своим
   API-ключом. Подделать входящий запрос можно, заставить ApiPay ответить
   «оплачено» — нет.

Второй уровень появился не от хорошей жизни: ApiPay может присылать уведомления
без подписи (проверено — приходили с `hasSignature: false`). Отвергать их
полностью означало бы, что оплаты не засчитываются вовсе, а верить им на слово —
вернуть ту самую дыру. Запрос к ApiPay снимает выбор между этими крайностями.

Перед обращением к ApiPay сервер проверяет, что такой заказ у нас есть и ещё не
оплачен, — иначе чужими запросами можно было бы гонять нас по чужим счетам и
жечь лимит в 200 запросов в минуту.

```
Браузер → POST /api/vote/start → сервер создаёт счёт в ApiPay, пишет payment(pending)
Kaspi   → человек подтверждает оплату в приложении
ApiPay  → POST /api/webhooks/apipay  ①подпись ②сумма ③выдача (один раз) 
Браузер → GET /api/payment/{id}/status → "paid" → показывает результат
```

Если webhook не дойдёт, опрос статуса сам спросит ApiPay через
`GET /invoices/{id}` и проведёт платёж тем же кодом. Отдельный cron не нужен.

## Что нужно заполнить

### 1. База данных (Supabase)

1. Создать проект на supabase.com.
2. SQL Editor → вставить целиком `supabase/migrations/0001_init.sql` → Run.
3. Project Settings → Database → Connection pooling → взять строку в режиме
   **Transaction** (порт 6543) → положить в `DATABASE_URL`.

Названия команд правятся в конце миграции или прямо в таблице `teams`.

### 2. ApiPay

`APIPAY_API_KEY` — уже прописан в `.env.local`.

`APIPAY_WEBHOOK_SECRET` — **отдельное значение, это не API-ключ.** Кабинет ApiPay
→ Настройки → вкладка «Подключение» → изменить ключ → «Адрес уведомлений».
Секрет выдаётся при создании webhook'а.

Адрес уведомлений указать такой:

```
https://ВАШ-ДОМЕН/api/webhooks/apipay
```

Без секрета система работает — неподписанные уведомления проверяются запросом к
ApiPay (см. «Главное про оплату»). Но задать его стоит: с подписью проверка
дешевле и не зависит от того, доступен ли ApiPay в эту секунду.

Проверить связь: кабинет ApiPay → «Проверить уведомления». В `/admin` появится
строка `webhook.test` с результатом `test_ok_signed` или `test_ok_unsigned` —
по нему сразу видно, подписывает ли ApiPay уведомления вообще.

### 3. Админка

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Полученное значение → `ADMIN_SESSION_SECRET`. Пароль → `ADMIN_PASSWORD`.
Вход: `/admin`.

## Режимы оплаты

`PAYMENTS_MODE` и `NEXT_PUBLIC_PAYMENTS_MODE` держать одинаковыми.

| Режим | Что делает |
|---|---|
| `offline` | В ApiPay не ходит вовсе. Можно смотреть сайт без ключей: кнопка «Тестілік төлемді растау» подтверждает оплату локально — но через тот же `confirmPayment`. |
| `sandbox` | Настоящие вызовы ApiPay ключом в ТЕСТ-режиме. Кнопка вызывает `POST /invoices/{id}/simulate-status`, ApiPay проводит счёт у себя и присылает **настоящий подписанный webhook**. Проверяется боевой путь целиком. |
| `live` | Боевые счета в Kaspi. Маршрут `/api/dev/pay` отвечает 404 — подтвердить им оплату нельзя даже зная адрес. |

## Как проверить, что всё работает

1. `PAYMENTS_MODE=sandbox`, ключ в ТЕСТ-режиме, webhook-секрет заполнен, адрес
   уведомлений указывает на развёрнутый сайт (для локальной отладки нужен туннель
   вроде `ngrok`, но у ApiPay боевой webhook требует настоящий HTTPS-домен).
2. Открыть `/dauys`, выбрать команду, ввести номер, нажать оплату.
3. Нажать «Тестілік төлемді растау».
4. Счётчик голосов должен вырасти, а в `/admin` — появиться платёж со статусом
   «оплачен».

Проверка защиты: нажмите тестовое подтверждение дважды. Голос должен добавиться
**один раз** — за это отвечает `UNIQUE (payment_id)` в таблице `votes`.

## Переход в боевой режим

По требованиям ApiPay:

1. Подключить кассира Kaspi — apipay.kz/connect-cashier. Без активной сессии
   кассира боевые счета сразу падают с `kaspi_session_not_configured`.
2. Заполнить профиль бизнеса — apipay.kz/business-profile.
3. Адрес webhook'а — на настоящем HTTPS-домене (не ngrok, не IP).
4. В кабинете переключить ключ с TEST на PRODUCTION.
5. Поставить `PAYMENTS_MODE=live` и `NEXT_PUBLIC_PAYMENTS_MODE=live`.

Известное ограничение ApiPay: у молодых организаций до прохождения проверки
действует лимит **1 счёт в сутки** в боевом режиме (`kyc_daily_limit_reached`).
В песочнице лимита нет.

## Развёртывание на Vercel

1. Запушить репозиторий, импортировать проект в Vercel.
2. Settings → Environment Variables → перенести всё из `.env.local`.
3. `NEXT_PUBLIC_SITE_URL` — боевой домен.
4. Задеплоить, затем прописать адрес webhook'а в кабинете ApiPay.

## Админка

- **Оплаты** — сколько платежей и на какую сумму, по видам, за сегодня и всего.
  Видны и незавершённые: сколько человек начали оплату и не довели.
- **Голоса** — по каждой команде: оплачено, корректировка, итого. Кнопки
  `+1 +10 +100` и `−1 −10 −100`.
- **Журнал правок** — каждое нажатие с временем. Пишется в той же транзакции, что
  и сама правка, поэтому правка без записи в журнал невозможна.
- **Заявки** — оплаченные өтінім с резюме.

Наружу отдаётся **только итоговое число голосов**. Ни разбивки, ни журнала нет
ни на публичной странице, ни в ответе API — эти поля отсутствуют в схеме ответа
(`publicTeamView` в `src/lib/votes.ts`), так что их не видно ни в исходниках
страницы, ни во вкладке Network.

## Что где лежит

```
src/lib/payments-core.ts   выдача голосов/билетов/заявок — единственное место
src/lib/webhook-signature.ts  проверка подписи ApiPay
src/lib/apipay.ts          клиент ApiPay
src/lib/start-payment.ts   создание счёта и синхронизация статуса
src/lib/repo.ts            SQL-запросы
src/app/api/webhooks/apipay/route.ts   обработчик webhook'а
supabase/migrations/       схема базы
docs/superpowers/specs/    проектная спека
```

## Безопасность

- Подпись webhook'а сверяется по **сырому** телу запроса, до разбора JSON,
  сравнением с постоянным временем.
- Сумма считается на сервере при создании счёта и сверяется при подтверждении.
  Прислать «10 голосов за 200 ₸» с клиента нельзя.
- Повторные webhook'и (ApiPay ретраит до 11 раз) гасятся `UNIQUE (payment_id)`.
- API-ключ только на сервере, в клиентский бандл не попадает.
- Ограничение частоты: не более 8 счетов на номер и 20 на IP за 10 минут —
  чтобы нельзя было засыпать чужой номер счетами в Kaspi.
- Cookie админки: httpOnly, secure, подписанная; срок внутри подписи.

**API-ключ ApiPay пересылался в переписке — после запуска его стоит перевыпустить
в кабинете.**
